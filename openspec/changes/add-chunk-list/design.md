## Context

当前系统采用 PDF 解析流水线：版面分析 → OCR 识别 → 元素标注。标注界面右侧面板以"元素列表"展示当前页面所有解析元素，左侧面板渲染 PDF 页面并在 SVG 覆盖层上绘制元素 bbox。元素列表与 PDF 视图之间已实现双向滚动同步和高亮联动（单元素级别）。

现有数据模型中，元素通过 `PdfElement` 表示，包含 `category_type`（类型）、`poly`（bbox 坐标）、`order`（排序序号）等字段。元素存储在 `PdfInfo.pdf_info[]` 数组中，按页组织，无结构分组信息。

本设计引入分块（Chunk）概念，将同页相邻文本类元素按 reading order 合并为段落块，同时表格/图片独立成块，提供更高层次的文档结构视图。

## Goals / Non-Goals

**Goals:**
- 基于 `order` 序列自动合并元素为分块，用户拖拽排序后分块自动重算
- 支持多栏文档的列布局自动检测和分栏合并
- 分块选中时左侧 PDF 视图高亮所有子元素 bbox
- 分块展开可查看子元素列表
- 分块只读，不引入编辑复杂度

**Non-Goals:**
- 不支持手动创建/拆分/合并分块（v2 可扩展）
- 不跨页分块，每页独立计算
- 不持久化分块数据（派生计算）
- 不修改后端 API 或数据格式
- 不修改元素列表的现有行为

## Decisions

### 1. 分块计算基于 order 序列

**选择**: 按 `order` 排序后遍历元素，按策略合并

**理由**: 
- order 是元素的当前排序状态，用户拖拽重排后会更新
- 分块与用户可见的元素顺序一致
- 实现简单，O(n) 单次遍历

**备选**: 基于空间 Y 坐标排序 → 拒绝，因为与用户手动排序状态可能不一致

### 2. 分块数据不存储，通过 useMemo 派生

**选择**: Chunk 数组通过 `useMemo(() => computeChunks(elements), [elements])` 计算

**理由**:
- 分块是确定的（相同输入 → 相同输出），无需额外状态
- 避免存储与推导数据的一致性维护问题
- elements 变化（编辑/新增/删除/排序）自动触发重算

**备选**: 存储在 Store 中 → 拒绝，增加状态管理复杂度且无必要

### 3. 多栏检测用 X 坐标聚类

**选择**: 收集非跨栏元素的 left 坐标，用双峰检测判断是否为双栏

**理由**:
- 当前数据模型无 column 元数据，只能从坐标推断
- 双峰检测（如 Jenks Natural Breaks 或 KMeans K=2）对典型学术论文双栏布局足够
- 不需要引入额外依赖

**备选**: 
- 从版面分析结果获取 column 信息 → 拒绝，当前 API 不输出此数据
- 固定 X 分割线（如页面中点）→ 不够灵活

### 4. Chunk 高亮复用现有 SVG overlay 机制

**选择**: 在 LeftPanel 的 SVG overlay 中，当 `selectedChunkId` 非空时，为 chunk 内所有元素绘制半透明填充 + 外围虚线边界框

**理由**:
- 无需修改现有 SVG 渲染架构
- 与单元素高亮共享相同渲染路径
- 虚线框提供 chunk 整体的视觉范围感知

### 5. Chunk 与 Element 选中互斥

**选择**: Chunk 选中和 Element 选中互相独立，同时只有一个生效（element 优先）

**理由**:
- 简化交互逻辑：用户同时只能有一个"关注焦点"
- Element 优先保证与现有行为向后兼容
- 当元素被选中时，其所在的 chunk 可被动高亮显示（视觉上关联）

### 6. Caption 归属逻辑

**选择**: figure_caption / table_caption 自动归入前一个对应类型的独立 chunk

**理由**:
- Caption 是附属于 figure/table 的，逻辑上应在一起
- 通过类型匹配（前一个 standalone chunk 的类型）自动查找归属
- 如果找不到对应主体（罕见情况），将 caption 作为 text 处理

## Risks / Trade-offs

- **[Risk] 多栏检测误判** → 在不规则布局或单栏中出现双栏误判 → **缓解**: 设置最小栏间距阈值（如 15% pageWidth），不足时退化为单栏
- **[Risk] 大页数文档分块计算性能** → 每次 elements 变化都重算 → **缓解**: 单页 elements 通常 <100 个，O(n) 算法性能可忽略
- **[Risk] 用户修改 element type 后分块变化不符合预期** → 如将 table 改为 text → **缓解**: 即时重算，用户可见变化效果；v2 可考虑加确认提示
- **[Trade-off] 分块不可编辑** → 自动分块可能不完美 → 用户可通过拖拽调整 order 间接影响分块结果，v2 可扩展编辑能力

## Open Questions

- 是否需要分块级别的搜索/筛选功能？→ v1 不从，v2 可根据反馈加入
- 是否需要在导出 ZIP 中包含分块信息？→ v1 不包含，分块是前端视图层功能
- Header/Footer 是否应该忽略而不是参与分块？→ v1 参与合并，保持简洁
